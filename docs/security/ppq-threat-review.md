# PPQ managed-account money paths — focused threat review

**Scope:** `rust/src/ppq/`, `rust/src/lib.rs` (PPQ regions), and `android/app/src/main/java/dev/disobey/mango/` (AppManager, MainActivity, `ui/ppq/*.kt`).

**Verdict:** **BLOCK** — the code cannot ship as-is. Two high/critical findings break the duress contract and can silently overwrite a user's BYOK or live PPQ account.

## Findings

| Severity | Location | Description | Exploit scenario | Remediation |
|---|---|---|---|---|
| critical | `rust/src/lib.rs:2580-2581` | `handle_confirm_forget` is the only sensitive-action handler that does **not** branch on `verify_sensitive_auth` returning `Err("duress")`. It returns the literal string `"duress"` to the caller and never invokes `ppq_duress_response`. | An attacker who has coerced the duress PIN during **Remove from this device** learns that the duress PIN matched (the error is `"duress"` instead of the generic `"sensitive_authentication_failed"`), and the device fails to wipe/enter decoy mode. The action also fails to preserve the PPQ credentials as required by plan §4.6/§6.5. | Mirror the pattern in `handle_ppq_backup_export`, `handle_confirm_delete_all`, and `handle_ppq_backup_restore`: if `code == "duress"`, call `ppq_duress_response(actor_state, core_tx)` and return its generic failure. |
| high | `rust/src/lib.rs:1966-1973` | `handle_ppq_provision` only blocks when `app_state.ppq.mode == Managed`. It does not block `PpqAccountMode::ExternalKey`, which `classify_startup` returns when a `mango::ppq-ai` key exists but `mango.ppq::credit-id-v1` does not (`rust/src/ppq/account.rs:66`). | A user with an existing BYOK PPQ API key reaches the **Set up PPQ automatically** flow. The actor calls `POST /accounts/create`, writes a new `credit_id`, and overwrites the existing `mango::ppq-ai` key with a new device key. The original BYOK key is silently lost and the user may lose access to the original PPQ balance. | Reject `PpqAccountMode::ExternalKey` in the early-exit guard or reuse the `already_managed` logic in `ppq::account::provision_account`. Switching from BYOK to managed must be a separate, explicit flow. |
| high | `rust/src/lib.rs:2422-2546` | `handle_ppq_backup_restore` can replace an existing managed account without an explicit conflict-acknowledgement or preflight. It overwrites credentials via `store_provisioned` after only a same/different `credit_id` check. | A user with a funded managed account restores an old `.mppq` backup. The actor silently overwrites the live credentials with the old ones. The current `credit_id`/device key is lost, and the live PPQ balance becomes inaccessible. The plan §4.5/§6.4 preflight (backup first, show balance/unknown warning, replace confirmed) is missing. | Add a `backup_risk_acknowledged` parameter to the FFI and require the native UI to show the conflict preflight with the current safe balance, unknown-balance warning, and explicit replace confirmation before calling this handler. |
| medium | `rust/src/lib.rs:2652-2654` | In `wipe_local_install(UserRequestedFullReset)`, the result of `PpqSecretStore::delete_all_verified()` is logged and discarded. | A user requests **Delete All Data**. The PPQ root credential and/or device key fail to delete (e.g. keychain commit failure). The UI still receives `ResetResult { success: true }`, and a subsequent startup may classify the leftover credentials as `RecoverablePartialState`, giving a false sense of wipe. | Propagate the `delete_all_verified` error: if it returns `Err`, return `Err(...)` from `wipe_local_install` so the caller can report `success: false` and keep the preflight open. |
| medium | `android/app/src/main/java/dev/disobey/mango/MainActivity.kt:79-83` | `openDocumentLauncher` copies the entire picked file into a `ByteArrayOutputStream` with no size cap before sending it to Rust. | An attacker who can get the user to select a maliciously large file can cause OOM / app crash before Rust rejects the file at `RECOVERY_FILE_MAX_BYTES` (64 KiB, `rust/src/ppq/recovery.rs:58`). | Cap the copy at `ppq::recovery::RECOVERY_FILE_MAX_BYTES` and do not copy more than that into memory. Surface `invalid_file` if the read reaches the cap. |
| medium | `android/app/src/main/java/dev/disobey/mango/PpqBackupCoordinator.kt:27`, `android/app/src/main/java/dev/disobey/mango/ui/ppq/PpqBackupDialog.kt:278-280`, `android/app/src/main/java/dev/disobey/mango/MainActivity.kt:76-89` | `PpqBackupCoordinator.onPpqImportResult` is a global singleton that stores a closure capturing the backup password and app PIN. The closure is not nullified if the user cancels the SAF picker or if an exception occurs. | The backup password and current PIN live in a long-lived global Kotlin object. If the app is inspected, crashes, or the user cancels, these secrets persist in a static field and are accessible to any later code on the main thread. | Do not capture secrets in a global closure. Use a request ID and have `MainActivity` deliver the byte result through a `ViewModel`/state-holder the dialog observes, clearing the captured auth data immediately on dismiss, cancel, or exception. |
| low | `rust/src/ppq/client.rs:187` | `create_lightning_invoice` only checks `wire.lightning_invoice.len() < 20` and does not validate that the invoice starts with `lnbc` or `lntb`. | A malicious or buggy PPQ response could return a non-Lightning string. It is persisted in `PendingInvoice`/`PpqFundingSummary` and rendered as a QR/invoice text until `PpqUiLogic.buildLightningUri` rejects it at wallet-open time. | Reject with `PpqError::InvalidResponse` unless `lightning_invoice` starts with `lnbc` or `lntb` and contains no whitespace. |
| low | `rust/src/ppq/recovery.rs:178-196` | `decrypt_recovery_document` reads the `kdf_id` byte at offset 6 but never validates it against `KDF_ID` before running Argon2id. | A crafted backup file can set any `kdf_id` value yet still be processed with Argon2id parameters. While the AAD mismatch will fail AEAD for a modified header, the file format intent is not enforced and a future KDF could be silently treated as Argon2id. | Add `if bytes[6] != KDF_ID { return Err(RecoveryError::UnsupportedBackupVersion); }` immediately after the version check. |
| low | `rust/src/ppq/recovery.rs:82-92` | `InnerDocument` uses plain `String` for `credit_id` and `api_key`. After serde round-trips, these intermediate strings are freed but not zeroized. | The decrypted plaintext is zeroized as `Zeroizing<Vec<u8>>`, but the parsed `inner` and its field strings may remain in freed heap. On a rooted/instrumented device, this widens the memory exposure window. | Use `Zeroizing<String>` for the secret fields of `InnerDocument`, or manually zeroize `inner`/`plaintext` before returning. |
| low | `rust/src/lib.rs:1515-1535` | `CoreMsg` variants `CreatePpqRecoveryBackup` and `RestorePpqRecoveryBackup` carry `backup_password: String` and `SensitiveActionAuth::MainPin { pin: String }` as plain `String`. | The sensitive-auth PIN and backup password sit in the actor message queue without zeroization. They are dropped when processed, but a heap snapshot could recover them. | Wrap the `backup_password` and `pin` strings in `Zeroizing<String>` in `CoreMsg`, `FfiApp` signatures, and `SensitiveActionAuth`. |
| low | `android/app/src/main/java/dev/disobey/mango/ui/ppq/PpqUiLogic.kt:50-52` | `copyInvoiceToClipboard` does not mark the clip as sensitive. | On Android 13+, the BOLT11 invoice appears in the system clipboard history and may be synced or shown in the keyboard suggestion strip. | For API 33+, set `ClipDescription.EXTRA_IS_SENSITIVE` to `true` on the `ClipData` before calling `setPrimaryClip`. |
| low | `rust/src/lib.rs:2406-2412`, `rust/src/lib.rs:2449-2501` | Argon2 KDF and, in restore, a blocking network validation run directly on the actor thread. | A complex backup password or slow network blocks the actor and can cause the Android UI to hang while waiting for the synchronous `FfiApp` reply. | Run Argon2 in `tokio::task::spawn_blocking`; keep the restore network call async and avoid `rt.block_on` inside the actor loop. |
| low | `rust/src/lib.rs:2077-2079`, `rust/src/lib.rs:2277-2283` | When invoice creation fails with `Offline`, the `uncertain` flag is set but the error code is not suffixed with `_uncertain`, unlike `ProvisionFailed`. | The user cannot tell whether an invoice may have been created at PPQ, and the UI does not surface the dedicated `InvoiceCreationUncertain` state from the plan. | Append `_uncertain` to the error code when `uncertain` is true, matching `ProvisionFailed`. |
| low | `rust/src/ppq/client.rs:207` | `invoice_status` builds the path with `format!("/topup/status/{invoice_id}")` without URL-encoding `invoice_id`. | A PPQ response with an `invoice_id` containing `?`, `&`, or `#` would alter the HTTP request query/fragment. | Use `percent-encoding` on the segment or build the URL with `reqwest` so the path segment is encoded. |
| low | `rust/src/ppq/account.rs:147-156`, `rust/src/ppq/contracts.rs:49-75` | `reconcile_unknown_by_balance` compares decimal strings lexically without normalizing leading zeros. | If PPQ returns balances with leading zeros (e.g. `"01.00"`), the app may incorrectly treat an unchanged balance as a funding increase or miss a real increase. | Normalize integer/fraction strings (strip leading zeros from the whole part, pad fractions) before comparison. |
| low | `rust/src/ppq/client.rs:325-336` | `PpqClient::request` does not handle HTTP 402; it falls through to `PpqError::InvalidResponse`. | A 402 from PPQ is mapped to a generic `invalid_response` instead of an explicit insufficient-balance signal, so the UI cannot route the user to top-up. This is a plan §6.10 gap but does **not** trigger automatic payment. | Add a 402 arm returning a new `PpqError::InsufficientBalance` and map it to a public error code in `handle_ppq_event` / `ppq_error_code`. |

## Verified OK (non-exhaustive)

- `PpqAccountSummary`, `PpqFundingSummary`, `PpqSetupPhase`, and `PpqFundingPhase` contain no `credit_id`, API key, backup password, or PIN.
- `AppAction` does not carry secrets; backup/restore are one-shot `FfiApp` direct calls, not long-lived `AppAction` state.
- `PpqBackupDialog` and `PpqRestoreDialog` use plain `remember` (not `rememberSaveable`) and clear fields in `DisposableEffect.onDispose`.
- `PpqSecretStore::store_provisioned` writes `credit_id` before `api_key`, reads both back, and does a constant-time comparison.
- Duress wipe uses `WipeMode::DuressPreservePpq` and does **not** call `PpqSecretStore::delete_all_verified()`; it preserves `mango.ppq::credit-id-v1`.
- `load_post_unlock` short-circuits PPQ classification when `duress_decoy_mode` is true.
- `PpqClient` enforces HTTPS (or loopback), caps response bodies at 256 KiB, and redacts errors.
- No raw `credit_id`, `api_key`, or `bolt11` values are logged in the Rust PPQ modules or Android PPQ UI.
- No automatic payment or invoice retry is triggered by 402, `InvoiceStatusValue::Unknown`, or `RateLimited`; polling respects `next_poll_at`.
- `lightning:` URIs are validated to start with `lnbc`/`lntb` and contain no whitespace before intent launch.
- The `.mppq` envelope uses a 44-byte AAD covering magic, version, KDF id, Argon2id parameters, salt, and nonce.

## Notes

- `rust/src/ppq/account.rs:77` defines `provision_account` with the intended `already_managed` guard and balance-after-store ordering, but it is currently **dead code**. The live route is `handle_ppq_provision` (`rust/src/lib.rs:1966`), which is why the external-key guard was missed.
- The high/critical items (duress forget leak, external-key overwrite, restore replacement ack, delete verification, and import size cap / password retention) should be the first blockers to resolve.
