## Deviations from Plan

### [Rule 3 — Blocking] Re-exported `mango_core::OrchestratedComponent`

- **Found during:** Task 2 read-first (drafting the helper function signature).
- **Issue:** The plan's action specifies `use mango_core::attestation::{AttestationStatus, OrchestratedComponent}` or "the equivalent re-export path", but `rust/src/lib.rs:12` declares `mod attestation;` (private). The previous re-export line (`pub use attestation::{AttestationError, AttestationStatus};`) included `AttestationStatus` only. The iced UI cannot name `OrchestratedComponent` in a function signature without the type being reachable from the crate root.
- **Fix:** Extended the re-export to `pub use attestation::{AttestationError, AttestationStatus, OrchestratedComponent};`. The type was already `#[derive(uniffi::Record)] pub struct` — this only makes it nameable from external Rust callers (does not change the UniFFI wire shape, since UniFFI generates Kotlin/Swift bindings for any `uniffi::Record` regardless of crate-root re-export).
- **Files modified:** `rust/src/lib.rs`.
- **Commit:** `a8b3115` (bundled with Task 2 — the fix is required for Task 2 to compile).
- **Why this is correct:** Rule 3 (auto-fix blocking issue) applies — the plan presupposes the iced crate can reach `OrchestratedComponent`. The fix is minimal and additive; no behavior change anywhere else in the codebase.

### [Plan no-op] No additional `AttestationStatus::Verified` match sites in iced beyond the four cited

- **Found during:** Task 1 grep sweep.
- **Issue:** The plan flagged four sites (`attestation_badge.rs:25`, `:34` for `status_label`/`detail_text`, `chat.rs:152`, `onboarding.rs:395`). A whole-tree `grep -rn AttestationStatus desktop/` confirms these are exhaustive — no other iced files pattern-match the unit variant. (`onboarding.rs:506` references `AttestationStatus::Failed { reason }` which is unchanged.)
- **Fix:** None needed; recorded for transparency.
