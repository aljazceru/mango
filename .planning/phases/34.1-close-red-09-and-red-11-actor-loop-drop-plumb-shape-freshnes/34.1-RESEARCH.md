## Approach: extend `AttestationStatus::Verified` to a struct variant (recommended)

**Decision (matches CONTEXT):** Add three nullable fields to the existing `Verified` variant.

```rust
#[derive(uniffi::Enum, Clone, Debug, PartialEq)]
pub enum AttestationStatus {
    Verified {
        shape: Option<String>,
        freshness: Option<String>,
        orchestrated_components: Option<Vec<OrchestratedComponent>>,
    },
    Unverified,
    Failed { reason: String },
    Expired,
}

#[derive(uniffi::Record, Clone, Debug, PartialEq)]
pub struct OrchestratedComponent {
    pub label: String,  // "gateway" | "model" | "compose_manager"
    pub value: String,  // hex address / actions hash
}
```

**Why this works:**
- uniffi 0.29 supports struct variants in `uniffi::Enum` — `AttestationStatus::Failed { reason }` (line 37) is the existing precedent in the same enum.
- `Vec<(String, String)>` is **not** representable across UniFFI (tuples don't bind). Promote to a `uniffi::Record` (`OrchestratedComponent`) with two named String fields. The label/value naming is generic — preserves room for future component types without rename.
- All three sub-fields are `Option<_>` so non-Redpill backends (Tinfoil, PPQ, Venice) construct `Verified { shape: None, freshness: None, orchestrated_components: None }` — no semantic change for them.
- The Kotlin/Swift binding cost is one breaking-but-mechanical change at every `AttestationStatus.Verified` reference: bare reference (e.g. `is AttestationStatus.Verified`) becomes destructure (e.g. `is AttestationStatus.Verified -> { val v = it; ... }`). The compilers in all three native platforms will surface every site.

**Why not a parallel struct (rejected, matches CONTEXT):** Would require a second collection on AppState keyed by backend_id, force every native UI to correlate two collections, and leave the original status hollow. The additive enum extension keeps the renderer site singular. Already documented as the preferred path.

## SQLite migration plan

### `MIGRATION_V19` (additive — no data backfill)

```sql
ALTER TABLE attestation_cache ADD COLUMN shape TEXT;
ALTER TABLE attestation_cache ADD COLUMN freshness TEXT;
ALTER TABLE attestation_cache ADD COLUMN orchestrated_components TEXT;
```

Three nullable TEXT columns; SQLite ALTER TABLE supports the form without DEFAULT for nullable cols. Existing rows have NULL — `deserialize_status("verified")` round-trips to `Verified { shape: None, freshness: None, orchestrated_components: None }` for them. No data loss; cache hits on pre-V19 rows simply lack the sub-line metadata until the next live verification re-populates the cache (5-min TTL per `attestation/redpill.rs:38`).

### Encoding decisions

- `shape`: store the canonical strings `"Flat" | "Orchestrated" | "Chutes"` directly (already what `verify_backend_attestation` produces). Treat as opaque on read.
- `freshness`: `"PerRequest" | "PerEnclave"`. Same.
- `orchestrated_components`: `serde_json::to_string(&Vec<(String, String)>)` → `[["gateway","0xAA"],["model","0xBB"],["compose_manager","0xCC"]]`. JSON because (a) variable-length, (b) cache.rs already imports `serde_json`-friendly patterns elsewhere, (c) we keep the canonical (label, value) ordering serialized as a list-of-pairs (not an object) so duplicate-label edge cases survive.

### Cache code changes

- `AttestationCache::put` — bind 3 additional params; for non-Redpill (`record.shape == None`), pass NULL.
- `AttestationCache::get` and `get_latest_for_backend` — SELECT the three new cols, deserialize JSON for components (defensive: `unwrap_or(None)` if JSON malformed — never panic on cache poisoning).
- The actor handler at `lib.rs:7431-7445` constructs `AttestationRecord` with the three values populated, so the cache write path is naturally wired once both ends know the fields.

### Rollback safety

ALTER TABLE ADD COLUMN is forward-only in SQLite. If a rollback to pre-V19 binary opens a V19 DB: harmless (extra columns ignored) **except** that `user_version` will read as 19 and `run_migrations` will skip them — so the rollback binary will not re-apply V19, which is correct. No risk.
