### ENC-02: Usearch vector index files encrypted with AES-256-GCM using DEK (Phase 28) — PARTIAL

Phase 28-03 built the encryption capability: `VectorIndex::save(dek: Option<&[u8; 32]>)` calls `file_crypto::encrypt_file` when a DEK is provided. However, the integration checker confirmed that **all 5 production call sites** in `lib.rs` pass `None`:
- Line 2911: `VectorIndex::new(&vector_data_dir, None)` 
- Line 4020: `actor_state.vector_index.save(None)` — DeleteDocument
- Line 4221: `actor_state.vector_index.save(None)` — DeleteMemory
- Line 5276: `actor_state.vector_index.save(None)` — EmbeddingComplete
- Line 5354: `actor_state.vector_index.save(None)` — MemoryExtractionComplete

**Root cause:** `ActorState` has no `dek` field. After `SetupPin` or `UnlockWithPin` derives the DEK hex, it's used for `open_encrypted` and then dropped. No mechanism carries the DEK bytes to subsequent VectorIndex operations.

**To close:** Add `dek: Option<Zeroizing<[u8; 32]>>` to `ActorState`; populate in `SetupPin`, `UnlockWithPin`, and `BiometricResult` handlers; pass to all `VectorIndex::new`/`save` call sites.
