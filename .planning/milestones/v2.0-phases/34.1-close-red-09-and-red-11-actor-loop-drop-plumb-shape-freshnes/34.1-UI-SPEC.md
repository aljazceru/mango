# Phase 34.1 — UI Design Contract

> Visual and interaction contract for the trust-UI sub-line additions on Settings → Providers. Generated by gsd-ui-researcher; verified by gsd-ui-checker.
>
> Scope is intentionally narrow: two text sub-lines under the existing Verified pill, on three platforms (Android Compose, iOS SwiftUI, Desktop iced). **No new components, no badge redesign, no layout changes.** The existing `ProviderStatusPill` / `AttestationBadge` aesthetic is preserved exactly.

---

## Design System

This is a native, multi-platform application — not a web app. shadcn does not apply. Each platform uses its native design system; the contract in this spec is the cross-platform copy + structural rules that all three renderers must mirror.

| Property | Value |
|----------|-------|
| Tool | none (native UI on each platform) |
| Preset | not applicable |
| Component library | Android: Material 3 (`androidx.compose.material3`); iOS: SwiftUI system styles; Desktop: iced widgets |
| Icon library | Inline UTF-8 glyphs only for this phase: `✓` (U+2713) for verified component, `✗` (U+2717) for failed component, `•` (U+2022) as separator. No icon-font dependency added. |
| Font | Platform default (Android Roboto / iOS SF / iced default) |

---

## Spacing Scale

Sub-lines render inside the existing expanded provider-row column. They reuse the row's existing spacing — no new tokens introduced.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Vertical gap between stacked sub-lines |
| sm | 8px | (existing) gap between badge row and first sub-line |
| md | 16px | (existing) row horizontal padding |

Exceptions: none. Sub-lines do NOT introduce indentation, leading bullets, or nested padding beyond the row column's existing `start = 12.dp, end = 12.dp` (Android) and equivalents on iOS / iced.

---

## Typography

Sub-lines are secondary metadata under the Verified pill. They use the platform's smallest body/label style with the muted secondary text color — same style currently used for `teeTypeLabelProviders(...)` and `backend.models.take(3).joinToString(...)` in `SettingsProvidersScreen.kt:163-167, 199-203`.

| Role | Android Compose | iOS SwiftUI | Desktop iced |
|------|-----------------|-------------|--------------|
| Sub-line text | `MaterialTheme.typography.labelSmall` | `.font(.caption2)` | iced `text(...)` at 12 px (matches existing `attest_label`) |
| Sub-line color | `MaterialTheme.colorScheme.onSurfaceVariant` | `.foregroundColor(.secondary)` | iced theme `text` color (default — same as `attest_label`) |
| Weight | regular (default) | regular (default) | regular |
| Line height | platform default | platform default | platform default |

The sub-lines are NOT bold, NOT colored as success-green, and NOT given their own surface chip. They are plain muted text — the Verified pill above them already carries the success color.

---

## Color

This phase introduces zero new colors. The Verified pill above the sub-lines continues to use the existing healthy-green token:

| Role | Existing Token | Where Used |
|------|----------------|------------|
| Verified pill foreground/background | `DarkHealthy` / `LightHealthy` (Android `theme/*`); `.verified` color (iOS `AppColors.swift`); existing iced healthy color | `ProviderStatusPill` and equivalents — UNCHANGED by this phase |
| Sub-line text | platform `onSurfaceVariant` / `.secondary` / iced default | New sub-lines added below the pill |

The `✓` glyph in the orchestrated breakdown inherits the sub-line text color (muted secondary) — it is NOT rendered green. The verifier already failed-closed if any component verification was wrong; the presence of the breakdown is itself the success signal, so per-component coloring is redundant and would conflict with the 60/30/10 hierarchy by adding a second accent surface.

The hypothetical `✗` glyph (failed component) would render in the existing destructive token (`DarkFailed` / `LightFailed` / iced failed color). However, in current implementation the verifier rejects the entire attestation if any component fails — so `orchestrated_components` is only populated when all three passed. The `✗` rendering branch is reserved for a future state and is NOT visually exercised by Phase 34.1. Spec preserves it for forward-compat.

## Copywriting Contract

The two sub-lines are the entire copy surface this phase introduces. Copy is locked verbatim — translations / tone changes are out of scope.

| Element | Copy | Render Condition |
|---------|------|------------------|
| Freshness sub-line | `Verified for this enclave instance` | `AttestationStatus.Verified` AND `freshness == "PerEnclave"` |
| Orchestrated breakdown sub-line | `gateway ✓ • model ✓ • compose ✓` | `AttestationStatus.Verified` AND `orchestrated_components` is non-empty (typically `shape == "Orchestrated"`) |
| Component label map | `gateway` → `gateway`, `model` → `model`, `compose_manager` → `compose` | Used to build the breakdown line — labels come from the `Vec<OrchestratedComponent>` `label` field, mapped through this dictionary so `compose_manager` shortens to `compose` |
| Unmapped component label fallback | render the raw `label` value as-is | Forward-compat: a future component type with an unknown label still renders rather than dropping |
| Separator | ` • ` (space, U+2022, space) | Between component entries in the breakdown line |
| Per-component success glyph | ` ✓` (space then U+2713) | Trailing each component label when verified |
| Per-component failure glyph | ` ✗` (space then U+2717) | Reserved — not rendered by current verifier behavior |

### Copy decisions (locked)

- Freshness sub-line is rendered ONLY for `freshness == "PerEnclave"`. For `freshness == "PerRequest"` the sub-line is NOT rendered (the per-request semantic is the implicit default for the platform; surfacing it on every row would dilute the signal and clutter the providers list). Confirmed by RESEARCH.md §"Risks & Open Questions" item 8.
- Both sub-lines may render simultaneously (Shape B + PerEnclave is not currently produced by any provider, but the renderer must support the combination if it ever appears). Stack order: freshness sub-line first, breakdown sub-line second, separated by xs (4 px) vertical gap.
- No CTA, no empty-state, no error-state, no destructive action introduced by this phase. The "Remove" provider button on the same row is pre-existing and unchanged.

### Primary CTA / empty / error / destructive — not introduced

| Element | Status |
|---------|--------|
| Primary CTA | Not introduced. Existing "Enable" / "Set Default" / "Remove" buttons unchanged. |
| Empty state | Not introduced. When `orchestrated_components` is `None` or empty the breakdown sub-line is simply not rendered — no placeholder copy. |
| Error state | Not introduced. Failed/Expired attestations continue to use the existing `Attest Failed` / `Attest Expired` pill labels in `attestationStyleProviders(...)`. |
| Destructive confirmation | Not introduced. |

## Interaction & State Contract

### States rendered (per provider row, when expanded)

| Attestation status | Pill label (existing) | Freshness sub-line | Breakdown sub-line |
|--------------------|-----------------------|---------------------|--------------------|
| `Verified { freshness: Some("PerEnclave"), orchestrated_components: None, .. }` (Shape C — Chutes) | Attested | "Verified for this enclave instance" | not rendered |
| `Verified { freshness: Some("PerRequest"), orchestrated_components: Some([gateway, model, compose_manager]), .. }` (Shape B — Orchestrated) | Attested | not rendered | "gateway ✓ • model ✓ • compose ✓" |
| `Verified { freshness: Some("PerRequest"), orchestrated_components: None, .. }` (Shape A — Flat) | Attested | not rendered | not rendered |
| `Verified { shape: None, freshness: None, orchestrated_components: None, .. }` (non-Redpill providers, or pre-V19 cache rows) | Attested | not rendered | not rendered |
| `Unverified` | Unverified | not rendered | not rendered |
| `Failed { reason }` | Attest Failed | not rendered | not rendered |
| `Expired` | Attest Expired | not rendered | not rendered |

### Visibility

- Sub-lines render ONLY in the **expanded** provider row on Settings → Providers (i.e. inside `AnimatedVisibility(visible = isOpen)` on Android, equivalent on iOS / iced). They do NOT render in the collapsed row's compact pill area.
- Sub-lines render ONLY on Settings → Providers — NOT in the chat top-bar attestation indicator, NOT in onboarding, NOT in the model picker. (Confirmed by CONTEXT §"Native UI" — trust UI is the providers screen.)
- Re-attestation refresh (5-min TTL) updates the sub-lines reactively via the existing `AppState.attestationStatuses` flow — no manual refresh affordance introduced.

### Interaction

Sub-lines are non-interactive read-only text. No tap target, no hover, no tooltip, no copy-to-clipboard on the hex values (the hex `value` field of each `OrchestratedComponent` is intentionally NOT rendered in v1 — only the `label` is shown, prefixed with the success glyph).

## Cross-Platform Parity Contract

The three native renderers MUST produce visually equivalent sub-lines. "Equivalent" = same copy, same render conditions, same stack order, same secondary-muted text style. Exact pixel-perfect parity is NOT required — each platform uses its native typography token.

| Platform | File | Insertion point |
|----------|------|-----------------|
| Android | `android/app/src/main/java/dev/disobey/mango/ui/SettingsProvidersScreen.kt` | Inside the expanded `Column` in the provider Card (after the `Row` containing health pill + attestation label, around line ~196). Reuse `MaterialTheme.typography.labelSmall` + `onSurfaceVariant`. |
| iOS | `ios/Mango/Mango/SettingsProvidersView.swift` | Inside the expanded provider section, after the existing attestation-style label (near line 241). Use `.font(.caption2)` + `.foregroundColor(.secondary)`. |
| Desktop iced | `desktop/iced/src/views/settings_providers.rs` | Inside the existing row column, after `attest_label` (lines 41-46). Use the existing iced `text(...)` builder used by `attest_label` for visual parity. |

The `AttestationBadge` reusable widget (`AttestationBadge.kt`, `AttestationBadgeView.swift`, `widgets/attestation_badge.rs`) MUST stay single-line. Sub-lines belong to the row composable, not the badge widget. (CONTEXT §"Native UI" — locked.)

## Out of Scope (explicit non-goals)

- Redesigning the Settings → Providers screen layout
- Changing the existing `ProviderStatusPill` / `AttestationBadge` shape, color, padding, or copy
- Adding sub-lines to chat top-bar, onboarding, model picker, or any non-providers screen
- Rendering hex `value` of orchestrated components (intentionally hidden in v1; future "details" affordance can surface)
- Coloring the per-component `✓` glyph green
- Localizing the copy (English-only, matching the rest of the app in v1)
- Adding tooltips, popovers, or "what is this?" affordances around the sub-lines
- iOS / iced screenshot tests (manual visual gate per CONTEXT §"Testing")
